    Reds

    redis过期事件实现延时任务缺点

    通过pub、sub的模式，默认的channel ：keyevent@0__:expired 用来监听key的过期事件

    时效性差

    过期事件是在Redis服务器删除key的时候通知，而不是过期的时候通知的

    Redis服务器删除key的时候两种策略

    1. 只有取出key的时候进行过期检查
    2. 定期删除：每隔一段时间抽取一批key进行删除过期的key的操作。但是限制删除操作的时长和频率，避免影响到CPU的操作。因此可能超过了过期时间，还没被删除，无法发出过期事件

    可能丢失信息

    多服务会重复接受消息

    因为只有广播模式，所有的消费者都可以接受到，多个实例介绍到之后，需要处理重复，增加代码开发难度和维护成本

    Redisson延迟队列的原理

    Redisson：java语言的Redis的客户端，提供了很多开箱即用的功能，分布式锁的实现、延时队列

    RDelayedQueue根据SortedSet有序集合，设置一个分数来代表权重，设置过期时间

    zrangebyscore找到所有的过期元素，加入到就绪消息列表中，这个阻塞队列一有消息进入就会被消费者监听，避免了轮询SortedSet，提高执行效率

    1. 减少了丢消息的可能
    2. 不存在重复消费

    缓存读写策略

    Cache Aside Pattern（旁路缓存模式）

    读请求比较多的情况

    写：
    1. 更新DB
    2. 再删除cache
    读：
    1. 从cache中读取，成功就直接返回
    2. 读取不到，就从DB中读取，再放在cache中
    注意：

    不可以先删除cache，因为cache写入速度比DB写入速度快很多

    缺点：
    1. 首次请求无cache
    2. 写频繁的话，缓存经常被删除，会影响缓存命中率
    解决
    1. 强制一致性：更新db的时候同时更新key
    2. 短暂允许DB和cache不一样的情况：更新db的时候，给cache一个很短的过期时间

    Read/Write Through Pattern（读写穿透）

    把cache视为主要数据存储，cache服务器帮助 读取和写入数据

    写
    1. 先查cache，如果cache不存在的话，直接更新DB
    2. cache存在的话，先更新cache，再更新DB
    读
    1. cache中读取到数据直接返回
    2. 读取不到，先从DB写入到cache，再返回

    Write Behind Pattern（异步缓存写入）

    Redis事务

    不支持原子性：

    Redis不支持回滚，更简洁性能更好，因为开发过程中发现错误，而不是生产中

    不支持持久性

    持久化方式：

    1. RDB
    2. AOF
    3. 混合

    AOF持久化更好，但是持久化策略的appendfsync的no（让操作系统决定，一般30s）和everysec（每秒同步）都存在数据丢失的风险；always（每次修改数据，都同步）基本可以满足，但是性能不好

    优化

    可以用redis lua脚本批量执行多条redis命令，提交到redis服务器一次性执行，减少开销

    不会被打断，但是还可能执行失败，无法回滚，不支持原子性，需要保证执行的命令都成功

    big key

    string 类型超过1M，符合类型元素超过5k个

    1. 设计不当：string类型存储大文件的二进制数据
    2. 规模考虑不当：快速增长的键值对
    3. 未及时清理数据
